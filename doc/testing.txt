1. Introduction                                                    *testing-intro*

testing.nvim is a test runner for Neovim plugins. It runs existing spec files
unchanged (the `return function(H)` styles of the author's plugins and busted
style `describe` / `it` specs, without plenary or busted), reports through a
terminal reporter, GitHub annotations, JUnit XML and a JSON result format, and
refuses to report a green run it cannot stand behind.

This release is pre-alpha. Spec files can run in a child editor of their own,
guards name what a spec leaves behind, unchanged spec files can come from a
result cache, and there is no editor UI beyond |:Testing|. The long form of this
help is in the repository's docs/ directory.

==============================================================================
2. Requirements                                               *testing-requirements*

  - Neovim 0.10 or newer
  - lib.nvim (hard dependency): https://github.com/StefanBartl/lib.nvim, at
    least the commits 6304829 (fs.write.atomic) and 89cb912 (safe_call keeps
    non-string errors)

The command-line runner looks for lib.nvim in four places, in this order:
$LIB_NVIM_DIR, <repo>/.deps/lib.nvim, <repo>/../lib.nvim and
stdpath('data')/lazy/lib.nvim. If it finds none, it names all four and exits
with 3. An override ($LIB_NVIM_DIR) that is set but invalid is a failure, never
skipped.

==============================================================================
3. Setup                                                             *testing-setup*

With lazy.nvim: >lua
    {
      "StefanBartl/testing.nvim",
      dependencies = { "StefanBartl/lib.nvim" },
      cmd = "Testing",
      opts = {},
    }
<
Without a plugin manager spec, call: >lua
    require("testing").setup({})
<
`setup()` is safe to call twice. The plugin file registers `:Testing` on its own,
so `cmd = "Testing"` lazy-loading works without `setup()`.

==============================================================================
4. Configuration                                                    *testing-config*

These are the options of `setup()`. The per-project file of the command-line
runner is a different thing, see |testing-project|. All keys are optional. A key
with the wrong type, and any unknown key, is dropped and reported with a
warning; the default stays in place.

                                                          *testing-notify_prefix*
notify_prefix ~
    Type: string, non-empty. Default: `"[testing]"`.
    Prefix of every message the plugin shows.

                                                              *testing-keymaps*
keymaps ~
    Type: table<string, string|string[]|false>|false. Default: `{}`.
    Overrides for the plugin's named keymap actions: action name -> new left-hand
    side, a list of them, or `false` to drop that action. `false` instead of a
    table binds no key at all. The plugin declares no action yet, so nothing is
    bound by default.

5. Commands                                                      *testing-commands*

                                                                       *:Testing*
:Testing [run] [{root}] [--file=..] [--filter=..] [--reporter=..] [--cached]
        [--no-cache] [--changed] [--since={rev}] [--shard={i}/{n}]
        Run the specs of the project in a headless child Neovim, never in this
        editor. {root} defaults to the nearest directory upwards that holds
        `.testing.lua`, `TESTS` or `.git`. `--cached` skips spec files whose
        inputs did not change since a green run (reported as cached);
        `--changed` and `--since` run only the specs the changes can reach (a
        partial run, never the "all green" last line).
:Testing file [{spec}]    Run the spec of the current buffer.
:Testing last             Repeat the last run.
:Testing list [{root}]    List what would run.
:Testing init [{root}] [--force] [--plugin={name}]
        Generate the test setup of a plugin repository. An existing file is
        never overwritten without `--force`.
:Testing conformance [{root}] [--gate] [--only={ids}] [--skip={ids}] [--bridge]
        Run the conformance checks K1..K15 on the project (a report; a failed
        gate is a warning, not an error).
:Testing surface [{root}] [--from={ir.json}] [--threshold={n}] [--markdown]
        The keymaps, commands and autocmds of the plugin and how much of them
        the specs exercised.
:Testing budget [{root}] [--update] [--factor={x}] [--allow-new]
        Measure the performance budgets of the runner. A measured case
        without a baseline entry compared nothing: exit 2 unless
        `--allow-new`.
:Testing cache stats | clear [{root}]
        Size of the result cache of the project, or delete it.
:Testing health           Run `:checkhealth testing`.
:Testing config           Show the effective plugin configuration.
:Testing doctor [{root}]  Show the project configuration and the dependency
                          report.

Subcommands and flags are completed with <Tab>. The complete reference is
docs/BINDINGS.md.

==============================================================================
6. Keymaps and autocommands                                      *testing-bindings*

The plugin binds no key and registers no autocommand by default. Every keymap it
gets later is a named action that can be moved or dropped through the `keymaps`
option.

==============================================================================
7. Health check                                                    *testing-health*

`:checkhealth testing` reports, in separate sections: the Neovim version; the
lib.nvim modules the plugin calls, plus two behaviors it relies on (safe_call
keeps non-string errors, fs.write.atomic refuses an invalid call), each probed
without writing anything; whether the kernel modules load; the dialect and
reporter registries; whether the command-line runner can find lib.nvim; the
`.testing.lua` of the current directory; the guards and the warm pool as that
file configures them (modes, allowances, pool size; a warning when every guard
is off, an error when a module of the isolation machinery does not load); the
effective configuration; whether the result cache directory can be written, whether
the documentation.nvim module graph of the affected selection is available and
current, and whether the conformance suite and the surface report load; and
whether |:Testing| is registered.

It is read-only, starts no process and loads no plugin that is lazy-loaded.
`.testing.lua` is a Lua file and loading it executes it, so the health check
does not: it evaluates the file in an empty environment with an instruction
budget. A plain table is validated for real; a file that needs more is reported
as "not evaluated here" (never as valid). `testing doctor` evaluates it.

A level never contradicts its text: an error is something broken, a warning is
something that will fail elsewhere (for example the command-line runner not
finding lib.nvim while the editor works), an info is something not checked.

8. Command-line runner                                                *testing-cli*

>sh
    nvim -n -i NONE --headless -u NONE -l scripts/testing.lua [run|list|doctor|budget|conformance|surface|explain|stamp|verify] [{root}] [options]
    nvim -n -i NONE --headless -u NONE -l scripts/testing.lua migrate [dry-run|apply] [{path}] [options]
<
Run it from {root}: specs that look at "this repository" read the working
directory and the runner does not change it. `scripts/test.sh` runs this
repository's own specs this way.

Subcommands: `run` (default), `list` (= `run --list`), `doctor` (resolved
configuration and dependency report), `migrate` (plan or write the move of a
repository to testing.nvim, see |testing-migrating|), `budget` (measure the hot
paths of a run against a baseline), `conformance` (the checks K1..K15) and
`surface` (the plugin's keymaps, commands, ... and what the specs exercised);
those two have their own arguments and exit codes (docs/CONFORMANCE.md,
docs/SURFACE.md). `explain` says why a spec file is selected, taken from the
cache, run or left out, and what its cache key is made of (see "Explain and
audit" below). `stamp` runs the suite and, after a complete green run, writes
the green stamp; `verify` answers from the cache keys, without running a spec,
whether the tree is still the stamped one (see "Stamp and verify" below).
`init` is available as |:Testing| init only.

Selection ~
  --file {text}      Only spec files whose file name contains {text}
                     (repeatable). `--only` is an alias.
  --filter {text}    Only cases whose name contains {text} (literal).
  --tags {a,b}       Only cases with one of these tags: a `#word` in a busted
  --exclude-tags     title, or a `-- @tags a b` header line in any spec.
  --lf, --ff         Only what failed last time, or that first.
  --order priority   Run first what failed last time, what the changes touch
                     and reach (nearest first), what has not run for long.
                     Orders only, never filters; excludes --shuffle.
  --order slowest-first
                     With --jobs 2 or more and child editors: the longest
                     files (remembered duration) start first. Results stay in
                     file order.
  --retry-failed {n} Run a red case again up to {n} times (1 to 10). A case
                     that passes on a retry is flaky: the run stays red, it is
                     listed and never cached.
  --allow-flaky      With --retry-failed: count such a case as green (still
                     listed). The run is then green-partial: no sentinel.
  --list, --dry-run  List what would run, run nothing.
  --shard {i}/{n}    Only shard {i} of {n} (CI matrices).
  --changed, --since {rev}, --affected[={rev}]
                     Only the specs the changes can reach (git, working tree
                     against HEAD, against {rev}, or the last commit). A
                     partial run: no "all green" last line. Anything that
                     cannot be placed selects every spec. Never the default.
  --consumers {dir}
                     With one of the three above: name the specs of the
                     checkouts below {dir} (projects that use this one) that
                     the change reaches (documentation.nvim). A hint, it never
                     changes what runs here. Also `affected.consumers` in
                     `.testing.lua`.
  --cache-dir {dir}  Base directory of the result cache (default stdpath('cache');
                     env TESTING_CACHE_HOME; the flag wins). `cache = {
                     project_key = ... }` in .testing.lua names the project
                     folder after a key instead of the checkout path
                     (docs/CI-CACHE.md).
  --cached, --no-cache, --cache-refresh, --cache-clear
                     The result cache: a spec file whose inputs are
                     byte-identical to an earlier green run does not run and is
                     reported as cached. Off unless asked for; --no-cache
                     always wins. docs/CACHE.md.
  --cache-audit {0..1|all}
                     Run that share of the cache hits anyway and compare with
                     the stored result. A difference is the finding
                     `cache.stale_pass` and exit 1; the measured stale-pass
                     rate is on the cache line and in `run.cache` of the IR.
                     Implies --cached; excludes --cache-refresh.
  --config {file}    Project file inside the root.
  --rtp {dir}        Add {dir} to the runtimepath (repeatable).

Control ~
  -x, --maxfail {n}  Stop after the first / {n}th failure.
  --shuffle, --seed {n}
                     Random order; the seed is printed.
  --case-timeout {ms}, --file-timeout {ms}
                     Timeouts. In this editor best effort (Lua code and
                     `vim.wait`, not a spec that blocks inside C); in a child
                     editor hard: the child and its process tree are killed.
  --strict           A skipped case or a discovery finding makes the run red.
  --isolated {none|file|case|soft}
                     `file`: every spec file in a child editor of its own (a
                     crash, a hang or a prompt ends that file only). `case`:
                     a child per case (busted). `soft`: this editor, what a
                     file changed is restored before the next. Default
                     `auto`: busted files `file`, the others `none`; a
                     `script` is always a child.
  --jobs {n|auto}    Child editors at once; the report is the same for any n.
  --watch            Run, then re-run on every change.
  --profile          Where the time went (stderr; `run.profile` in the IR).
  --pool-reuse, --no-pool-reuse
                     The warm pool: with `--isolated file` the files share
                     child editors that are reset and verified clean between
                     files (a member that cannot prove it is clean is
                     replaced and a finding says why). `script` files and
                     `case` never use it.
  --pool-size {n}    Editors the pool keeps (default min(--jobs, 4)).
  --guard {name}={mode}
                     Guards: fs, state, scheduled_error, prompt, deprecation,
                     process_net (off|warn|error), clock (on|off).
  --allow-fs {path}, --allow-spawn {exe}, --allow-network {host}
                     What the guards let through (repeatable).
  --no-determinism   A child keeps the parent's LANG/LC_ALL/TZ.
  --no-trace         No trace artifact for a child that timed out or died.
  --host {c|l}       A child starts like plenary's host (`c`, default) or like
                     `nvim -l`.
  --env-allow {name} An environment variable (or PREFIX*) a child may inherit.

Output ~
  --reporter {name}  Terminal reporter: term, github, junit, json or agent.
                     Default: $TESTING_REPORTER, then `agent` in a coding
                     agent environment ($TESTING_AGENT=1 forces it, =0 stops
                     the detection), else term.
  --agent-budget {n} Characters of the failure part of `agent` (default 4000).
  --format {text|jsonl}  Shape of `agent` (jsonl: one object per line).
  --json {file}      Write the Result-IR (schema_version 1), validated.
  --junit {file}     Write a JUnit XML report.
  --github           GitHub Actions annotations and step summary.
  --durations {n}    Name the {n} slowest cases.
  --sentinel {name}  Last line of a complete green run (default TESTING_OK).
  --no-timings       No timing line.

Explain and audit ~
  explain {spec}...  Say why a spec file is selected, taken from the cache, run
                     or left out: the reason of the selection, `hit`, `miss`
                     (which file, with old and new hash, which environment
                     variable by name, the Neovim version or the configuration
                     changed since the stored entry) or `uncacheable` (the
                     file and line of what makes it so, and the way out:
                     `-- @cache-allow`, `-- @cache-inputs`, `-- @cache-env`,
                     `env_allow`,
                     `-- @cache off`). {spec} is a path, a directory or a part
                     of a file name; the options of a run are accepted (the
                     key depends on them). It changes nothing.
    --all            Every spec file: the hit rate and the reasons of the
                     files without a key, most frequent first.
    --json           One JSON document (testing-explain/1).
    --parts          The lines the key is the hash of.
Stamp and verify ~
  stamp              A run that writes the green stamp after the verdict
                     `green` only (never for a partial or red run: exit 1;
                     options that select part of the suite are refused, exit
                     2). The stamp holds, per spec file, the cache key or the
                     reason there is none, plus runner, Neovim, OS and
                     configuration digests, commit and tree, all taken before
                     the first spec runs (an input that changed while the
                     specs ran: no stamp, exit 1). The report says so in its
                     first line (`RED ... exit 1`, `verdict: red`), never
                     green. No secrets.
    --out {file}     Where to write it (default: `stamp.json` in the state
                     directory of the project, not in the checkout).
    --note           Also attach it to the tree object as a git note under
                     refs/notes/testing.
  verify             Recompute the keys (after the `minit` of the project, as a
                     run does) and answer: `verified` (exit 0 and the
                     sentinel, only when EVERY file is proven), `partial`
                     (files without a key are not proven; never green),
                     `changed`, `rejected` (other runner, Neovim, OS or
                     configuration), `expired`, `dirty`, `untrusted`,
                     `invalid`, `no-stamp` (all exit 1).
    --stamp {file}   Read this stamp instead of the default one.
    --from-note      Read the git note of the tree of HEAD.
    --max-age {dur}  Oldest accepted stamp (7d; s, m, h, d).
    --allow-dirty    Check a dirty working tree anyway (said in the answer).
    --require-hmac   Refuse a stamp unless TESTING_STAMP_SECRET is set.
    --allow-unsigned In CI, accept a stamp without a checked HMAC (otherwise never green).
    --json           One JSON document (testing-verify/1).
                     TESTING_STAMP_SECRET (16 characters or more) adds an
                     HMAC when writing and checks it when verifying.
                     docs/CACHE.md, "Stamp".
  --cache-audit {0..1|all}
                     see Selection: a share of the hits runs anyway; a
                     difference is `cache.stale_pass`. A spec whose key gave
                     two different results is `nondeterministic` and not
                     cached (`-- @cache-allow nondeterministic` lifts it).
                     docs/CACHE.md.

An option that is parsed but not implemented is refused with exit code 2, never
ignored. Only a complete green run (no skipped case, no `--maxfail` stop, no
case accepted by --allow-flaky) prints the sentinel; anything else prints a
distinct last line. The same
distinction is the verdict line of every reporter: green, green-partial, red.

9. Project file .testing.lua                                      *testing-project*

A Lua file in the project root that returns a table; every key is optional. It
is executed, so it is loaded only from the root named on the command line (or
`--config`, inside that root), as text, below 256 KiB. Invalid values and
unknown keys are warnings (the default stays); an unusable file is exit 2.

  plugin       string       Module root of the project.
  roots        string[]     Spec roots, relative. Default { "TESTS" }.
  spec_pattern string[]     Lua patterns that make a file a spec. Default
                            { "_spec%.lua$" }. A malformed pattern is a
                            warning (the default stays).
  dialect      string|table "auto" (default), "testing", "a", "b", "c", "d",
                            "h", "busted", "script"; or { [path or glob] =
                            name, ["*"] = name }.
  assertions   string       "error" (default): a case without assertions
                            fails; "warn": it passes and is listed.
  isolated     string       "auto" (default), "none", "file", "case", "soft".
  guards       table        fs, state, deprecation, scheduled_error, prompt,
                            process_net: "off"|"warn"|"error" or a table
                            { mode = ..., categories, ignore_*, keep, allow,
                            ... } (docs/GUARDS.md); clock: boolean.
  guard_allow  table        { fs, spawn, network } string lists.
  pool         table        { size = n, reuse = boolean }: the warm pool.
  determinism  boolean      Fixed LANG/LC_ALL/TZ in a child. Default true.
  trace        boolean      Trace artifact of a child that died. Default true.
  soft_keep    string[]     Modules the soft isolation never unloads.
  jobs         integer|"auto" Child editors at once. Default 1.
  shard, watch, budget
               tables       `--shard` balance, `--watch` debounce and poll,
                            `testing budget` factor and baseline.
  cache        table        { enabled = boolean }: reuse results without
                            --cached (never in CI).
  conformance  table        gate, skip, waivers (each with a reason),
                            keymaps_off, timeout_ms, load_budget_ms,
                            rules_bridge: `testing conformance`.
  surface      table        track (the runner records what the cases
                            exercise), threshold, kinds, ignore, setup_chunk.
  host         string       "c" (default) or "l".
  filetype     boolean      Children run `filetype plugin indent on`.
  disable_first_run boolean Set lib.nvim's first-run opt-out
                            (vim.g.lib_nvim_deps_disable_first_run) in every
                            editor the runner starts, before `minit`. Default
                            true.
  env_allow    string[]     Environment names a child may inherit on top of
                            the allowlist (never NVIM*, never a bare "*").
  minit        false|string Minimal init, run before the specs.
  deps         string[]     Dependencies that must resolve (exit 3 if not).
  timeouts     table        case_ms (10000), file_ms (60000); hard in a child.
  setup        table        Options `setup()` is called with by conformance
                            and surface.
  coverage      table       bindings, commands, autocmds: 0..1 thresholds of
                            `testing surface`.
  snapshots, backends
                            Validated, reserved: nothing acts on them yet.

A dependency is looked up in $<NAME>_DIR, <root>/.deps/<name>, <root>/../<name>
and stdpath('data')/lazy/<name>; the message of a miss names all four.

10. Exit codes                                                  *testing-exit-codes*

  0   Every spec file passed.
  1   A case failed, errored, timed out or crashed (a child editor that died);
      under --strict also a skip or a discovery finding.
  2   Usage or configuration error, or nothing to run (also a selection that
      matches nothing).
  3   Infrastructure error: a dependency is missing, minit raised, a report
      could not be written, the editor was quit under the run, an internal
      error.

A spec cannot end the run: `os.exit` inside a spec is an error of that file
(in a child editor it is a `crash` of that file; the others run on).

`testing migrate`: 0 done or nothing to do, 1 (`--check`) work to do, 2 refused
or bad usage, 3 the root cannot be analysed.

11. Dialects                                                      *testing-dialects*

The dialect of a file is sniffed from its text (`dialect = "auto"`) or forced.

  a, b, c   `return function(H)` with the helpers of lib.nvim, of
            markdown/diff.nvim, of images.nvim. One case per file.
  d         `require("harness")` and `M.run()` (spotlight.nvim). One case per
            file.
  h         `return function(H)` on the project's own `TESTS/harness.lua`.
            One case per file. Never greener than that harness: collected
            failures, printed failure lines and fields named like a failure
            that grew are failures.
  script    A self-running file (own counters, `os.exit`): one case, run in a
            child editor of its own; the exit code and the printed `[FAIL]`
            lines are the verdict.
  busted    `describe` / `it` with before_each, after_each, setup, teardown,
            pending and a luassert subset. One case per `it`. Not supported,
            raising by name: spy, stub, mock, insulate, expose, finally,
            xdescribe, luassert extensions.

A failed check is recorded and the file goes on. A case without an assertion
fails; a file whose dialect cannot be told is an error case with the reason
(never a skip: set `dialect` in .testing.lua).

==============================================================================
12. Reporters and the Result-IR                                  *testing-reporters*

The Result-IR (`schema_version` 1) is deterministic JSON: run, cases, summary.
Statuses: pass, fail, error, skip, xfail, xpass, timeout, crash. Paths become
<REPO>, <HOME>, <TMP>, <STATE>; with --json the free text is redacted (user and
host name, environment pairs, e-mail addresses, `Users/<name>` path shapes) and validated
after writing. A privacy finding that redaction cannot remove becomes a top-level `warnings`
list; it never discards the verdict.
`effects` are filled by the guard layer; a case says so in its notes when the
guard that fills them is off. Additive fields: `cases[].cached` (not executed
in this run, from the result cache), `cases[].surface` (`surface.track`),
`run.cache`, `run.profile`, `run.verdict`.

The verdict (`run.verdict`, a line of every reporter) is `green` (every file ran
green or has a cache hit; the sentinel), `green-partial` (exit 0, but a
selection, a case filter or a skip means not everything was looked at: no
sentinel, the reasons are named) or `red` (exit 1; with the last green run and
the files changed since). It counts spec files: n from cache, m ran, k skipped
on purpose. The exit codes do not change.

Reporters read the IR only and treat everything from the code under test as
hostile input: `term` (default; a line that would start with `::` is written
`\x3A:`, so a failure message cannot forge a workflow command), `github`
(annotations escaped so a test name cannot start a workflow command, step
summary appended), `junit` (well-formed
XML for any input), `agent` (compact, for coding agents: the verdict as the
first line, then only the failures with file:line, expected/actual and a repeat
command; equal failures are one entry with a counter; a character budget counts
what it leaves out). A reporter that fails is exit code 3.

13. Migrating from busted or plenary                             *testing-migrating*

Specs stay unchanged. `testing migrate` reads the repository and prints the
plan (a `.testing.lua`, `scripts/test.sh`, `TESTS/minimal_init.lua` with the
state of the old `scripts/minimal_init.lua` carried over (that file is deleted),
the CI workflow as diffs, notes and risks); the created Lua files follow the
repository's `stylua.toml` (stylua on PATH; otherwise a note). `assertions` and
`timeouts` are notes, not written keys. `testing migrate apply` writes the plan
into a clean git working tree. Or by hand: check out lib.nvim where the runner finds
it, run the runner from the plugin root, read what it says about spec
locations, unknown dialects and unsupported luassert features, then point
scripts/test.sh and CI at the runner and remove the old one. See
docs/MIGRATING.md.
