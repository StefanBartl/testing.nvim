1. Introduction                                                    *testing-intro*

testing.nvim is a test runner for Neovim plugins. It runs existing spec files
unchanged (the `return function(H)` styles of the author's plugins and busted
style `describe` / `it` specs, without plenary or busted), reports through a
terminal reporter, GitHub annotations, JUnit XML and a JSON result format, and
refuses to report a green run it cannot stand behind.

This release is pre-alpha (milestone M1). All spec files share one Neovim
process, `effects` of a case are not measured, and there is no editor UI beyond
|:Testing|. The long form of this help is in the repository's docs/ directory.

==============================================================================
2. Requirements                                               *testing-requirements*

  - Neovim 0.10 or newer
  - lib.nvim (hard dependency): https://github.com/StefanBartl/lib.nvim, at
    least the commits 6304829 (fs.write.atomic) and 89cb912 (safe_call keeps
    non-string errors)

The command-line runner looks for lib.nvim in four places, in this order:
$LIB_NVIM_DIR, <repo>/.deps/lib.nvim, <repo>/../lib.nvim and
stdpath('data')/lazy/lib.nvim. If it finds none, it names all four and exits
with 3. An override ($LIB_NVIM_DIR) that is set but invalid is a failure, never
skipped.

==============================================================================
3. Setup                                                             *testing-setup*

With lazy.nvim: >lua
    {
      "StefanBartl/testing.nvim",
      dependencies = { "StefanBartl/lib.nvim" },
      cmd = "Testing",
      opts = {},
    }
<
Without a plugin manager spec, call: >lua
    require("testing").setup({})
<
`setup()` is safe to call twice. The plugin file registers `:Testing` on its own,
so `cmd = "Testing"` lazy-loading works without `setup()`.

==============================================================================
4. Configuration                                                    *testing-config*

These are the options of `setup()`. The per-project file of the command-line
runner is a different thing, see |testing-project|. All keys are optional. A key
with the wrong type, and any unknown key, is dropped and reported with a
warning; the default stays in place.

                                                          *testing-notify_prefix*
notify_prefix ~
    Type: string, non-empty. Default: `"[testing]"`.
    Prefix of every message the plugin shows.

                                                              *testing-keymaps*
keymaps ~
    Type: table<string, string|string[]|false>|false. Default: `{}`.
    Overrides for the plugin's named keymap actions: action name -> new left-hand
    side, a list of them, or `false` to drop that action. `false` instead of a
    table binds no key at all. The plugin declares no action yet, so nothing is
    bound by default.

==============================================================================
5. Commands                                                      *testing-commands*

                                                                       *:Testing*
:Testing [run] [{root}] [--file=..] [--filter=..] [--reporter=..]
        Run the specs of the project in a headless child Neovim, never in this
        editor. {root} defaults to the nearest directory upwards that holds
        `.testing.lua`, `TESTS` or `.git`.
:Testing file [{spec}]    Run the spec of the current buffer.
:Testing last             Repeat the last run.
:Testing list [{root}]    List what would run.
:Testing init [{root}] [--force] [--plugin={name}]
        Generate the test setup of a plugin repository. An existing file is
        never overwritten without `--force`.
:Testing health           Run `:checkhealth testing`.
:Testing config           Show the effective plugin configuration.
:Testing doctor [{root}]  Show the project configuration and the dependency
                          report.

Subcommands and flags are completed with <Tab>. The complete reference is
docs/BINDINGS.md.

==============================================================================
6. Keymaps and autocommands                                      *testing-bindings*

The plugin binds no key and registers no autocommand by default. Every keymap it
gets later is a named action that can be moved or dropped through the `keymaps`
option.

7. Health check                                                    *testing-health*

`:checkhealth testing` reports, in separate sections: the Neovim version; the
lib.nvim modules the plugin calls, plus two behaviors it relies on (safe_call
keeps non-string errors, fs.write.atomic refuses an invalid call), each probed
without writing anything; whether the kernel modules load; the dialect and
reporter registries; whether the command-line runner can find lib.nvim; the
`.testing.lua` of the current directory; the effective configuration; and
whether |:Testing| is registered.

It is read-only, starts no process and loads no plugin that is lazy-loaded.
`.testing.lua` is a Lua file and loading it executes it, so the health check
does not: it evaluates the file in an empty environment with an instruction
budget. A plain table is validated for real; a file that needs more is reported
as "not evaluated here" (never as valid). `testing doctor` evaluates it.

A level never contradicts its text: an error is something broken, a warning is
something that will fail elsewhere (for example the command-line runner not
finding lib.nvim while the editor works), an info is something not checked.

8. Command-line runner                                                *testing-cli*

>sh
    nvim -n -i NONE --headless -u NONE -l scripts/testing.lua [run|list|doctor] [{root}] [options]
    nvim -n -i NONE --headless -u NONE -l scripts/testing.lua migrate [dry-run|apply] [{path}] [options]
<
Run it from {root}: specs that look at "this repository" read the working
directory and the runner does not change it. `scripts/test.sh` runs this
repository's own specs this way.

Subcommands: `run` (default), `list` (= `run --list`), `doctor` (resolved
configuration and dependency report), `migrate` (plan or write the move of a
repository to testing.nvim, see |testing-migrating|). `init` is available as
|:Testing| init only.

Selection ~
  --file {text}      Only spec files whose file name contains {text}
                     (repeatable). `--only` is an alias.
  --filter {text}    Only cases whose name contains {text} (literal).
  --tags {a,b}       Only cases with one of these tags: a `#word` in a busted
  --exclude-tags     title, or a `-- @tags a b` header line in any spec.
  --lf, --ff         Only what failed last time, or that first.
  --list, --dry-run  List what would run, run nothing.
  --config {file}    Project file inside the root.
  --rtp {dir}        Add {dir} to the runtimepath (repeatable).

Control ~
  -x, --maxfail {n}  Stop after the first / {n}th failure.
  --shuffle, --seed {n}
                     Random order; the seed is printed.
  --case-timeout {ms}, --file-timeout {ms}
                     Timeouts. In this editor best effort (Lua code and
                     `vim.wait`, not a spec that blocks inside C); in a child
                     editor hard: the child and its process tree are killed.
  --strict           A skipped case or a discovery finding makes the run red.
  --isolated {none|file}
                     `file`: every spec file in a child editor of its own (a
                     crash, a hang or a prompt ends that file only). Default
                     `auto`: busted files `file`, the others `none`; a
                     `script` is always a child.
  --jobs {n}         Child editors at once; the report is the same for any n.
  --host {c|l}       A child starts like plenary's host (`c`, default) or like
                     `nvim -l`.
  --env-allow {name} An environment variable (or PREFIX*) a child may inherit.

Output ~
  --reporter {name}  Terminal reporter.
  --json {file}      Write the Result-IR (schema_version 1), validated.
  --junit {file}     Write a JUnit XML report.
  --github           GitHub Actions annotations and step summary.
  --durations {n}    Name the {n} slowest cases.
  --sentinel {name}  Last line of a complete green run (default TESTING_OK).
  --no-timings       No timing line.

An option that is parsed but not implemented is refused with exit code 2, never
ignored. Only a complete green run with no skipped case prints the sentinel; a
selection, `--maxfail` or a skip prints a distinct last line.

9. Project file .testing.lua                                      *testing-project*

A Lua file in the project root that returns a table; every key is optional. It
is executed, so it is loaded only from the root named on the command line (or
`--config`, inside that root), as text, below 256 KiB. Invalid values and
unknown keys are warnings (the default stays); an unusable file is exit 2.

  plugin       string       Module root of the project.
  roots        string[]     Spec roots, relative. Default { "TESTS" }.
  spec_pattern string[]     Lua patterns that make a file a spec. Default
                            { "_spec%.lua$" }.
  dialect      string|table "auto" (default), "testing", "a", "b", "c", "d",
                            "h", "busted", "script"; or { [path or glob] =
                            name, ["*"] = name }.
  assertions   string       "error" (default): a case without assertions
                            fails; "warn": it passes and is listed.
  isolated     string       "auto" (default), "none", "file".
  jobs         integer      Child editors at once. Default 1.
  host         string       "c" (default) or "l".
  filetype     boolean      Children run `filetype plugin indent on`.
  disable_first_run boolean Set lib.nvim's first-run opt-out
                            (vim.g.lib_nvim_deps_disable_first_run) in every
                            editor the runner starts, before `minit`. Default
                            true.
  env_allow    string[]     Environment names a child may inherit on top of
                            the allowlist (never NVIM*, never a bare "*").
  minit        false|string Minimal init, run before the specs.
  deps         string[]     Dependencies that must resolve (exit 3 if not).
  timeouts     table        case_ms (10000), file_ms (60000); hard in a child.
  setup, conformance, coverage, snapshots, backends
                            Validated, reserved: nothing acts on them yet.

A dependency is looked up in $<NAME>_DIR, <root>/.deps/<name>, <root>/../<name>
and stdpath('data')/lazy/<name>; the message of a miss names all four.

==============================================================================
10. Exit codes                                                  *testing-exit-codes*

  0   Every spec file passed.
  1   A case failed, errored, timed out or crashed (a child editor that died);
      under --strict also a skip or a discovery finding.
  2   Usage or configuration error, or nothing to run (also a selection that
      matches nothing).
  3   Infrastructure error: a dependency is missing, minit raised, a report
      could not be written, the editor was quit under the run, an internal
      error.

A spec cannot end the run: `os.exit` inside a spec is an error of that file
(in a child editor it is a `crash` of that file; the others run on).

`testing migrate`: 0 done or nothing to do, 1 (`--check`) work to do, 2 refused
or bad usage, 3 the root cannot be analysed.

==============================================================================
11. Dialects                                                      *testing-dialects*

The dialect of a file is sniffed from its text (`dialect = "auto"`) or forced.

  a, b, c   `return function(H)` with the helpers of lib.nvim, of
            markdown/diff.nvim, of images.nvim. One case per file.
  d         `require("harness")` and `M.run()` (spotlight.nvim). One case per
            file.
  h         `return function(H)` on the project's own `TESTS/harness.lua`.
            One case per file. Never greener than that harness: collected
            failures, printed failure lines and fields named like a failure
            that grew are failures.
  script    A self-running file (own counters, `os.exit`): one case, run in a
            child editor of its own; the exit code and the printed `[FAIL]`
            lines are the verdict.
  busted    `describe` / `it` with before_each, after_each, setup, teardown,
            pending and a luassert subset. One case per `it`. Not supported,
            raising by name: spy, stub, mock, insulate, expose, finally,
            xdescribe, luassert extensions.

A failed check is recorded and the file goes on. A case without an assertion
fails; a file whose dialect cannot be told is an error case with the reason
(never a skip: set `dialect` in .testing.lua).

==============================================================================
12. Reporters and the Result-IR                                  *testing-reporters*

The Result-IR (`schema_version` 1) is deterministic JSON: run, cases, summary.
Statuses: pass, fail, error, skip, xfail, xpass, timeout, crash. Paths become
<REPO>, <HOME>, <TMP>, <STATE>; with --json the free text is redacted (user and
host name, environment pairs, e-mail addresses, `Users/<name>` path shapes) and validated
after writing. A privacy finding that redaction cannot remove becomes a top-level `warnings`
list; it never discards the verdict.
`effects` are not collected yet; every case says so.

Reporters read the IR only and treat everything from the code under test as
hostile input: `term` (default), `github` (annotations escaped so a test name
cannot start a workflow command, step summary appended), `junit` (well-formed
XML for any input). A reporter that fails is exit code 3.

==============================================================================
13. Migrating from busted or plenary                             *testing-migrating*

Specs stay unchanged. `testing migrate` reads the repository and prints the
plan (a `.testing.lua`, `scripts/test.sh`, `TESTS/minimal_init.lua` with the
state of the old `scripts/minimal_init.lua` carried over (that file is deleted),
the CI workflow as diffs, notes and risks); the created Lua files follow the
repository's `stylua.toml` (stylua on PATH; otherwise a note). `assertions` and
`timeouts` are notes, not written keys. `testing migrate apply` writes the plan
into a clean git working tree. Or by hand: check out lib.nvim where the runner finds
it, run the runner from the plugin root, read what it says about spec
locations, unknown dialects and unsupported luassert features, then point
scripts/test.sh and CI at the runner and remove the old one. See
docs/MIGRATING.md.
